# Agent Note: 移出上下文的确认改为居中对话框

Status: implemented

[English](2026-09-23-context-removal-confirmation-dialog.md) | 中文

## Problem

把提问移出模型上下文原先在提问面板内确认，形式是列表上方的一条横栏（[逐回合移出上下文](2026-09-22-per-turn-context-removal.zh.md)）。面板从输入框底座向上展开，因此这条横栏会把它正在询问的那些行向下挤走，恰好挤出刚刚按下垃圾桶入口的指针下方：读者按下某一行的入口，那一行就移动了。横栏还只认指针——没有任何按键可以确认，也没有任何按键可以取消——并且多选时它把提问正文藏在被自己挤走的列表里，读者确认五个提问的移除时看不到将要离开的是什么。

内联位置只有一个理由：面板在外部指针按下时关闭，渲染在面板之外的确认会被那次抵达它的按下顺手关掉。

## Decision

**确认是覆盖遮罩页面的居中模态对话框**，由共享的 `Modal` 原语构建并 portal 到 document body，因此无论面板锚定在哪里，它都位于视口中部。面板不再在指针下重排，移除也读起来像它本该有的那种重要决定。

**对话框存在期间暂停外部按下规则。** `QuestionNavigator` 从移除状态推导出 `removalOpen`，在其成立期间不安装面板的 `pointerdown` 监听；正是这一点让面板之外的确认成为可能。于是面板留在遮罩之后，取消后读者回到同一处列表位置。

**回车确认，Esc 取消。** 对话框通过 `Modal` 自身的关闭路径拥有 Esc 与遮罩，`QuestionNavigator` 在 `confirm` 状态期间绑定回车。正在执行的请求两者都不响应：它撤下回车绑定，设置 `dismissable={false}`，并禁用两个底部按钮，因此同一次移除不会被发送两次。

**对话框列出将要离开的提问。** 它在数量那句话下方列出每个待移除回合已加载的提问正文，因为遮罩挡住了读者刚做的选择。已加载窗口没有边界的回合对应的提问不会列出——与它不可被勾选是同一条规则。

**全选补全了多选。** 选择模式新增一个入口：勾选当前屏幕上所有可移除的行，全部勾中后再次按下则清空。它只作用于可见行，因此不会悄悄勾选被查询过滤掉的提问；没有可移除的可见行时它禁用。

**勾选是列表上的手势，而不是读者必须先找到的模式。** 按住 Cmd/Ctrl 点击一行即增删这一项；按住 Shift 点击则按列表当前的顺序勾选锚点与该行之间所有可移除的行，因此被过滤的列表只在读者看得见的范围内连选，而不涉及隐藏的历史。两种按法都会进入选择模式，最后一次勾选所针对的行成为锚点。没有锚点的 Shift 点击——或锚点已被查询过滤掉的 Shift 点击——勾选自己这一行并成为新的锚点，因为只有一端可达的区间不是区间。在不可移除的行上按修饰键点击什么都不做：既不勾选，也不跳转 transcript。显式的模式开关保留，旁边的提示写明这些手势。

**按住 Shift 即进入实时连选，被 hover 的那一行始终在其中。** Shift 被作为按住状态跟踪：指针停在某一行上按下 Shift，无需点击就勾选该行以及回到锚点之间所有可移除的行，指针移动则重算区间。每次重算都从手势开始时持有的勾选出发，因此划回去时区间会缩小，而不是把划过的行全部累积起来。松开 Shift 即提交——做法是忘掉那个起点；丢失的 keyup（手势进行中窗口失焦）同样释放，因此区间不会无形地一直开着。

**Esc 一次退一层：先取消进行中的连选，再退出选择模式，最后关闭面板。** 取消实时连选会精确恢复手势开始时的勾选，并留在选择模式内。没有进行中的连选时，Esc 退出选择模式并清空勾选；两者都没有时关闭面板——这在此之前没有任何键能做到。移除对话框存在期间，Esc 只属于对话框。

## Alternatives considered

**保留横栏，只加按键。** 否决：被挤走才是问题本身。会移动自己所描述列表的确认，无论能否用按键回答都是错的。

**把对话框锚定到面板（浮在导航栏上方的气泡）。** 否决：面板已经占满输入框底座到 transcript 区之间的高度，锚定卡片要么压住列表，要么在矮窗口里跑出视口——正是居中布局消除的那种失败。

**在 ui-chat 内自写一个 `role="alertdialog"` 卡片。** 否决：`Modal` 已经拥有遮罩、居中、body portal、Esc 与焦点可见样式，在功能包里再实现一遍会与共享对话框样式漂移。代价是通用的 `role="dialog"`；该对话框带 `aria-modal` 与标题，其中的失败信息带 `role="alert"`。

**单行移除不确认。** 否决：移除改变会话余下部分中模型能看到的内容，且无法从面板撤销；数量那句话是唯一说明记录仍保留在对话中的地方。

**面板打开时普通点击即勾选，完全不要模式。** 否决：普通点击是读者跳到某个提问的方式，面板首先就是为此存在的。修饰键点击在不占用列表已有手势的前提下加入了勾选。

**在已加载的提问上连选，而不是在显示的行上连选。** 否决：有查询时两者不同，会悄悄勾选被过滤掉提问的连选，移除的是读者从未看到名字的回合。可见顺序是读者唯一能据以推理的顺序。

**把 Shift 区间做成预览，点击才提交。** 否决：那需要在已勾选与未勾选之间再加第三种行状态，而读者为了留住眼前已经看到的结果仍得按一下。实时勾选复用列表已经绘制的状态，而预览想要防住的失误由 Esc 兜住。

**面板里不绑定 Esc，或者只给它一种固定含义。** 两端都否决。不绑定时，划过头的连选没有便宜的退路：读者必须把每一行错选逐个点回去，而在长列表上建起来的选择重建代价很高——正是这个代价让取消值得它那点接线，而那不过是面板本就需要的监听上多出的一个分支（Esc 关闭面板本身也要它）。只给一种固定含义比不绑定更糟：只用来关闭面板，Esc 会丢掉读者花力气做出的选择；只用来取消连选，面板就一直拒绝每个浮层都会响应的键。这个阶梯让每一次按下都是当下最小的撤销，而它的层级在屏幕上都看得见——进行中的连选、复选框、面板——读者能预测哪一层会响应。

**已提交的连选也能用 Esc 撤销。** 否决：Shift 一旦松开，屏幕上就分辨不出某个勾选来自划选还是来自点击，只撤销"最后一次划选"的 Esc 作用在不可见的历史上。取消止于它所属的那次手势；下一层——退出选择模式——才是诚实的粗粒度撤销。

## Testing

`packages/client/ui-chat/tests/question-navigator.client.spec.tsx` 覆盖该对话框：单行与多选确认、列出的提问正文、回车确认与 Esc 取消、无关按键不改变待确认状态、执行中的移除拒绝第二次回答并拒绝关闭、在 portal 出的对话框内按下不会关闭面板、全选只勾选与清空可见的可移除行、失败对话框报告拒绝原因并关闭，以及列表手势：Cmd/Ctrl 点击进入选择并增删一项、Shift 点击取走锚点与自身之间的可移除行并跳过进行中的回合、没有可达锚点的 Shift 点击只勾选自己这一行、修饰键点击不可移除的行什么都不做。按住 Shift 的划选另有自己的用例：被 hover 的行连同其区间一起进入勾选、指针划回时区间缩小、hover 到不可移除的行不增加任何勾选、松开即提交因而之后的 Esc 取不回来、Esc 取消进行中的连选并恢复到起始勾选、Esc 阶梯依次经过连选、选择模式与面板，以及移除对话框存在期间 Esc 归对话框。

## Consequences

- `QuestionNavigator` 通过 `dsh-client-ui-primitives` 的 `Modal` 与 `Button` 渲染；面板内联确认的样式已删除，取而代之的是 `ChatView.module.css` 中对话框的列表、按键提示与危险操作类。
- 面板的 `pointerdown` 监听现在是有条件的。今后任何同样渲染在面板之外的控件，应扩展同一条暂停规则，而不是新增第二条规则。
- 取消确认后选择仍然保留，因此误点一次移除的代价是一次 Esc，而不是重建整个选择。
- 锚点是行的 seq，只在面板打开期间保留。关闭面板、退出选择模式和一次落地的移除都会清空它，因此之后的 Shift 点击不会从读者早已忘记的行开始连选。
- macOS 把 Ctrl 点击交付为右键手势，所以那里的勾选修饰键是 Cmd，Ctrl 服务 Windows 与 Linux。两者在所有平台都接受，而不按平台分支。
- 面板打开期间会在 document 上监听 Shift 与 Esc。按住 Shift 会在没有任何点击的情况下改变勾选，因此这个面板里今后任何读取 Shift 的控件，都必须说明该手势归谁。
