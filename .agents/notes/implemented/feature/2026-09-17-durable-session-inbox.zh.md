# Agent Note：持久化的会话收件箱

状态：已实现

[English](2026-09-17-durable-session-inbox.md) | 中文

## 问题

用户在多个 Workspace 里同时跑许多 Agent 会话，下班离开一夜后回来，没有任何持久记录告诉他发生了什么：侧边栏的绿色"已完成"小圆点是浏览器内存里的一个位，选中或刷新就清掉；[汇总面板](2026-09-01-cross-workspace-finished-session-digest.zh.md)永远列出所有已完成会话，却不知道哪些用户已经处理过；卡在审批或提问上的会话无人察觉地等待；也没有地方写下"明天跟进这个"并指回那段对话。状态模型只有一个瞬时位，而用户需要的是若干个持久状态。

## 决策

### 用户的决定存在 Host 上

`@deepseek-ai/dsh-session-inbox` 是 `sessionInbox` Remote 背后的存储域 sidecar。它按 Session 存储 `lastSeenSeq`（用户在屏幕上看到过的最高日志 seq；`markSeen` 只会抬高它）、`handledAt`、`snoozedUntil` 与 `pinned`；全局存储 `reviewedAt`；并存储指向某个 Session、可选地指向某条 `user/message` seq 的待办。每次读取与变更都返回完整快照，每次写入都发出 `session-inbox/changed`，经 `dsh-api-remotes` 允许列表转发到浏览器。Session 日志仍是 Agent 做了什么的记录；sidecar 是用户对它做了什么决定的记录，因此刷新、换浏览器、Host 重启都不会丢，多个浏览器无需合并即可收敛到同一快照。

"未读"是推导出来的，不是存储的：当汇总里最新落地的 seq（`replySeq`，未回答时为 `questionSeq`）超过 `lastSeenSeq`，该行即为未读。客户端在该 seq 出现在屏幕上时把当前会话标记为已读，因此打开会话会像绿点一样清除未读状态——但标记是持久的，行不会消失，而是移到"已读未处理"，直到用户标记已处理。

### 汇总投影携带收件箱需要的东西

`sessionDigest`（状态版本 2）新增 `questionSeq`、`questionAt`、`repliedAt`、从修改类工具自己的 `tool/result` `diffs[].path` 记录读出的改动文件记录（`changedFiles` 有界，`changedFileCount` 完整），以及之前提问的有界 `history`（含结果、回复时间与文件数）。这足以支撑按提问的时间线、指向某一问的待办，以及卡片上"改了 N 个文件"的一行，且仍随会话列表下发，每次打开零 I/O。

### 一个界面，按原因分区

汇总面板变成收件箱：行按需要关注的原因分区——置顶、等你回复、失败或中断、完成未读、已读未处理、运行中，以及按需显示的已处理——顺序如此，因为卡在审批上的 Agent 才是浪费一夜的那个。等你回复、失败、未读与置顶的行不受时间窗限制；时间窗（自上次查看、今天、近 7 天、全部）只约束上下文行。延后的行只计数不列出。工作区 chip 携带每个工作区的待处理数与运行中数。每张卡片提供打开、继续（打开并预填输入框）、已处理、加入待办、置顶与延后；键盘环（`j`/`k`、`Enter`、`e`、`t`、`p`、`s`、`Escape`）触达同样的操作。侧栏入口持有一个组合键 `Ctrl+1`，可从任何位置开关面板：它是整个会话期间都挂载的控件，而修饰键让这个组合键在输入框里依然有效——单字母的键盘环在那里必须保持沉默。"标记已查看"移动默认时间窗的起点；"复制晨报"把分区与未完成待办渲染为 Markdown。待办标签列出与会话和提问连接的待办，以及作为自动待办的失败会话；时间线标签把每条保留的提问放在它被提出的那一天。

三个小座位把面板与邻居连起来：ui-conversation 的 `chatReveal`（揭示请求经由每会话聊天 store 传递，聊天向前翻页直到该行加载）、ui-workspace 的 `sessionTodos`（右键菜单的"加入待办"把选中的 id 交给提供该座位的一方），以及 ui-renderer 的 `documentBadge`（待处理计数前缀到标签页标题）。每个座位对双方都是可选的。

## 考虑过的替代方案

**把已读标记存在浏览器里。** 否决：标记会因浏览器和 profile 而异，而要修的正是用户离开后没有存活下来的状态。

**把"未读"存为 Host 在 `turn/end` 时翻转的标志。** 否决：Host 需要知道哪个客户端在看；用 `lastSeenSeq` 对比汇总的落地 seq 推导未读不需要这种知识，而且后续回复落地时仍然正确。

**在 Host 上为失败轮次自动创建待办。** 否决：失败集合已可由汇总结果与已处理标记推导，存储它会成为可能与日志不一致的第二权威。

**在汇总入口旁边再加一个按钮。** 否决：两个整面入口都回答"我不在时发生了什么"，正是[提问轨道 note](2026-09-02-question-rail-reduced-to-stepping.zh.md) 在别处消除的重复；汇总入口直接长成收件箱。

**通过扫描对话的全局服务做基于滚动的揭示。** 否决：聊天视图已经拥有提问索引与翻页；请求只需要一个地址（`seq`）和一个可以持久等待的位置，每会话 store 正好提供。

## 后果

已完成的工作不再因为被查看而从记录中消失；它在用户控制下经历未读 → 已读 → 已处理，而等待用户的会话是收件箱最先显示的内容。每个标记和待办在连接到同一 Host 的任何浏览器中都可见。

`sessionDigest` 提升了状态版本，因此持久化投影缓存行会在下次折叠时重算。列表载荷因每行的有界历史与文件列表而增大（`historyQuestions`、`changedFilePaths` 预算）。已删除 Session 的标记会留在 sidecar 中直到其待办被删除；没有东西与之连接，所以不可见。

已读标记跟随选中而非阅读位置；延后时间固定为次日 09:00；面板仍是覆盖中间栏的界面切换。

## 验证

Host 测试固定了单调的 `markSeen`、已处理/延后/置顶的幂等性、`snooze-in-past`、待办文本校验与生命周期、排序稳定性、重启恢复与销毁准入。汇总测试固定了文件记录的收窄与上界、历史上界与新字段预算。客户端测试固定了分类与分区、时间窗与工作区筛选、chip 计数、时间线分组、待办连接、晨报文本、控制器的读取/推送/重同步/失败路径、已读标记订阅、徽标座位、`sessionTodos` 座位、经聊天 store 的 `chatReveal` 交接、键盘环，以及每个卡片与标签操作。`pnpm run test:gui` 除既有的 `directory-picker-native` Win32 探测外全部通过。
