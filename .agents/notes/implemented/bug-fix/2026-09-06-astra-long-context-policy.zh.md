# Agent Note: Astra 长上下文配置

Status: implemented

[English](2026-09-06-astra-long-context-policy.md) | 中文

## 问题

部署可能将 `gpt-6-astra` 声明为过时的 272,000 token 容量，而操作者要求使用 1,000,000 token 窗口。上下文仪表会如实显示适配器配置的容量。仅增大容量会使默认主动压缩阈值变为 800,000，而不是所需的 900,000。

## 决策

容量与推理等级仍由提供方设置显式声明。[提供方指南](../../../../docs/user/guide/providers.zh.md#astra-long-context)说明了 `contextWindow: 1000000`、`reasoningEfforts.max: max` 和 `agent-default-model` 选择。DSH 不根据模型名称推断端点能力，也不导入 Codex 配置。配置的输出上限与窗口容量相互独立，并可根据剩余上下文容量降低。

基础组合包与标准、Cordis、PTC 预设为精确路由 `openai/gpt-6-astra` 配置 `thresholdRatio: 0.9`。现有策略解析器在 1M 窗口下得到 900,000 token。其他路由保留后端默认的 80%。Web 禁用宿主后端，因此仅修改基础组合包条目无法调整 Web agent。

模型设置会到达下一次准备的请求，包括当前轮次的后续步骤。预设配置属于固定的组装代次：已有的驻留 agent 需要实际重建，或在进程重启后重新打开已保存的会话，才能使用新比例。刷新浏览器和发送下一轮消息不会替换该代次。

[按路由解析上下文的决策](../architecture/2026-07-20-routed-model-context-and-compaction-policy.zh.md)仍是权威说明：适配器拥有容量，压缩消费者拥有策略。这项配置应用该决策，不增加注册表或配置 API。

## 考虑过的替代方案

**仅修改仪表分母。** 适配器的溢出检测和主动压缩仍会使用错误容量。

**在适配器内硬编码 Astra 容量。** 模型 ID 无法证明网关的限制或访问权限。部署所属的模型设置保留优先级，并保持无关模型不变。

**向 LLM 适配器增加 Codex 风格的字段。** 现有比例已能在配置容量下表达所需阈值。压缩策略不属于模型传输选项，这项配置不需要额外的绝对上限 API。

**通过临时宿主插件重载当前预设引擎。** 一个预设代次可能服务多个活动 agent。重载压缩服务无法保证正在进行的压缩已结束；保留代次可以避免这一生命周期风险。

## 影响

仪表、准备后的模型元数据和压缩容量共享一个提供方设置。修改该设置会使比例阈值随之缩放，因此它不是独立的 900,000 token 上限。主动检查在步骤之间使用测量压力，提供方确认溢出时可以提前触发恢复。本地 1M 配置与协议格式测试不能证明外部端点接受完整的 1M 请求。

## 测试

基础组合包和随包预设的测试读取实际 YAML 策略条目。压缩测试验证 900K 阈值、160K 保留尾部以及相邻路由不变。真实 Loader 组装监听设置文件从 272K 到 1M 的变更，并验证 OpenAI Responses 请求携带 `reasoning.effort: max` 和配置的输出上限。无密钥的 [Astra Session 场景](../../../../snapshots/session/astra-context/session.v2.jsonl)运行随包交付的 headless 策略，在测量压力为 899,999 token 时继续执行，在 900,000 时压缩，并保留近期图片历史。其报告的用量和图片计价是合成数据；回放仍使用真实的计量器、压缩引擎和 Session 持久化。
